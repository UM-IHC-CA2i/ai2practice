Step 1 · The question

The question

Are patients sent for CT older than those sent for MRI?

It sounds like a two-line answer: work out the average age in each group and compare. In practice, data exported from a hospital system is messy. The same thing is written in different ways, values are missing, some are impossible, and some patients appear twice. Averages computed on messy data can be badly wrong, and nothing on the screen warns you. So this lab follows the order every clinical study follows: clean the data by stated rules, describe who is in it, look at it in a chart, and only then test the difference.

Your table, clinical, lists patients sent for CT or MRI with the columns patient_id, modality, age and sex. It has been made messy on purpose, in the ways real exports are: sex recorded as M, male, F or f; missing ages; a few impossible ages such as 999; and duplicate rows. The notebook states the cleaning rules, so everyone cleans the same way. As in Lab 1, the table is made up and generated from your GitHub username.

By the end of this lab you can:

  • Clean a messy table by written rules, and report how many rows each rule removed.
  • Build a "Table 1" that describes the patients in each group.
  • Compare two groups in a chart, such as a histogram or box plot.
  • Run a statistical test and explain what its p-value does and does not tell you.

Step 2 · The idea

Clean first, then compare

Data cleaning means finding and dealing with values that are wrong, missing or inconsistent before any analysis. Some rows are kept and corrected (writing "male" as "M" so it is counted with the other M rows); others are removed (a duplicate row, or an age of 999 that was really a code for "unknown"). Good practice is to write the rules down before you start and to report how many rows each rule removed, so a reader can judge whether the cleaning could have changed the answer.

Interactive: spot the messy rows

Twelve rows from an export (practice data). Click every row that needs work, either removing or correcting, then check your picks. Watch what the messy rows do to the average ages.

One impossible age turned the comparison upside down. That is why cleaning comes first, and why it is written into the notebook as code: anyone can rerun it and get the same rows.

Next comes Table 1, so called because it is the first table in nearly every clinical paper. It describes who was studied, group by group: how many patients, their age as a mean (the average) with a standard deviation (how spread out the values are), or as a median (the middle value) with an interquartile range when the values are skewed, and counts with percentages for categories such as sex. A reader looks at Table 1 to decide whether your patients resemble theirs.

Finally, even if the CT patients turn out a few years older on average, a difference that size could appear by chance in a small sample. A statistical test asks how surprising your difference would be if there were really no difference between the groups. Its answer is the p-value: a small p-value (by convention, below 0.05) means a difference this large would be unusual by chance alone. It does not tell you the difference is large, or that it matters clinically. For comparing two means, the notebook uses Welch's t-test.

Step 3 · Warm-up

Warm-up: read the code

Two short reading checks. They are not graded and always show the explanation. They also work as a skip test: they cover what the notebook's first parts teach.

What does this code print?

df = pd.DataFrame({"age": [70, 80, None, 999]})
df = df[df["age"] < 120]
print(len(df))

The middle line keeps only the rows where the condition is true. 999 fails it. The missing value (pandas shows it as NaN, "not a number") also fails, because any comparison with a missing value counts as false. That is handy here, but in the notebook you drop missing values on purpose with dropna(), so that you can count and report how many there were.

Warm-up: put it in order

Drag the lines into an order that gives the right mean age for each modality.

  1. means = df.groupby("modality")["age"].mean()
  2. df = pd.read_csv("clinical.csv")
  3. print(means.round(1))
  4. import pandas as pd
  5. df = df.drop_duplicates()

Cleaning has to happen before the summary: if the duplicates are still there when the means are worked out, a patient listed twice counts twice. groupby("modality") splits the table into a CT group and an MRI group, and ["age"].mean() averages the age column within each group. round(1) keeps one decimal place, which is how you report the numbers in step 5.

Skip test. If both were easy, you can move quickly through Part 1 (cleaning). Do not skip Part 4: reading a p-value correctly is the part most people get wrong.

What the coding modes mean

Every task in the notebook is tagged with one mode. In Write tasks you write a few lines yourself from an empty cell, with a hint and a hidden solution. In Fill in tasks most of the code is there and you complete the blanks. Reuse tasks import a function you wrote in an earlier lab from your own toolkit.py, the way real projects grow. In Direct the AI tasks you ask an AI assistant (Colab's built-in one is suggested, but any is fine) to write the code, paste it in, run the test cell, and note in the AI-use log what you asked and what you had to change. Fix tasks give you code "written by an AI" with one realistic mistake to find. Read tasks ask you to put lines in order or predict what code will print before you run it.

Early labs lean on writing code yourself, because that is how the basics stick. Later labs lean on reusing your code, directing an AI and checking its work, because that is how research code is written now, and checking is the part a person must still do.
